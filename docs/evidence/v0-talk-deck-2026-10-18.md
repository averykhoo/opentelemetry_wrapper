## Why the library exists (slides 4-14, 27)

- Apps emit signals (logs, traces, metrics) through an OTel library over OTLP to an OTel Collector (receiver,
  processor, exporter), which feeds one or more backends. The collector avoids every app speaking every backend's
  protocol. It also computes things such as RED metrics from HTTP spans.
- Three ways to instrument: vendor-instrumented components; auto-instrumentation ("No effort, low return": "you
  don't get any control over what's instrumented, and it doesn't include any app context"); and manual
  instrumentation ("Low (non-zero) effort, higher return": e.g. the user who called the endpoint, nested spans for
  specific function calls). The talk is about making the third one easy, for Python apps.
- "The library is only maintained to standardize our internal logging, although it's available for anyone to use."

## The problem: the plain OTel SDK (slide 16)

Twelve snippets from the official OTel Python docs: creating a tracer, spans, attributes, recording exceptions,
propagating and receiving context, OTLP export over HTTP and gRPC, console export, "...repeat for logs", "...repeat
for metrics". Notes: "Quite a bit of work is needed to manually instrument your code using the official OTEL
libraries"; "it's also ugly; this contravenes PEP 20 'The Zen of Python', line 1: 'Beautiful is better than ugly.'";
"to export logs you need to import some protected/internal things from the OTEL library, which will make your linter
complain".

## Design principles (slide 17), verbatim

- Safe
  - Never crashes the running application
  - Hard to use incorrectly
- Unsurprising
  - Simple, idiomatic, succinct, and pretty
  - Reasonable documented defaults
  - Emits zero logs/spans (of its own) at runtime
- Helpful
  - Semi-automated instrumentation
  - Machine-readable first, human-readable a close second
  - Enriches spans with available application context
  - Makes OTEL metrics scrapable via a Prometheus endpoint

Notes: "From most to least important: It has to be reasonably idiot proof / It has to always exhibit reasonable
behavior with minimal custom configuration / It should try to be as helpful as possible and require minimal developer
effort".

## Usage as shown (v0, slides 19-23)

- Configuration by environment variables: `OTEL_EXPORTER_OTLP_ENDPOINT` (no OTLP export by default),
  `OTEL_EXPORTER_OTLP_HEADER`, `OTEL_EXPORTER_OTLP_INSECURE`, `OTEL_EXPORTER_PROMETHEUS_ENDPOINT` (default `/metrics`).
- `instrument_logging(print_json=True)`, `instrument_requests()`, `instrument_sqlalchemy()` ("can be noisy and I don't
  recommend it by default"), `app = instrument_fastapi_app(FastAPI())`, `@instrument_decorate` on functions; or
  `instrument_all()` for logging, requests and dataclasses at once.
- Classes: `@instrument_decorate` on a class spans creation, method calls and property reads;
  `instrument_dataclasses()` instruments every later `@dataclass`; library classes too
  (`instrument_decorate(sortedcontainers.SortedList)()`).
- "Hard to get wrong": idempotent and async-compatible (seven stacked decorators through `async_to_sync` /
  `sync_to_async`), and "Prints everything as JSON, auto-converting non-JSON" (complex numbers, `Decimal`, modules,
  functions, classes, sentinels, stray arguments). Note: "I try reasonably hard to avoid breaking things when
  unexpected things happen".
- Without a collector: logs go to stdout/stderr as JSON for a log shipper, and Prometheus scrapes `/metrics`. With
  one: point the OTLP endpoint environment variable at it.

## Details appendix (hidden slides 29-35)

- **JSON conversion:** Pydantic models, anything FastAPI can encode (datetime, Decimal, ...), and unusual objects
  (functions, classes) by name through introspection. "TLDR we want to convert anything and everything to JSON".
  Long strings are truncated.
- **Application context:** user context from the `X-UserInfo` OIDC header (base64, then JSON, then flattened),
  upstream latency from response headers such as `X-Envoy-Upstream-Service-Time`, and the Kubernetes namespace and pod
  from the service account mount; OTel semantic conventions for the attribute names.
- **Code introspection:** unwraps decorated functions recursively, finds function, class, module, file and line for
  the span name, with an in-memory cache.
- **Instrumentation:** a custom JSON `logging.Formatter` on a root handler that doesn't clobber other handlers ("which
  means we cannot use OpenTelemetry's implementation"); FastAPI gets the OIDC header attributes and an optional
  Prometheus endpoint. "While programmatic un-instrumentation has been made possible, I didn't bother to write the
  code to do it since there was no use case for me".
- **Type-checking (BETA):** Pydantic type-checking and coercion, with a cache; compatible with Pydantic 1 (DEC-41
  keeps it in v0).
- **An example JSON log record:** the standard `LogRecord` fields plus `otelSpanID`, `otelTraceID`,
  `otelTraceSampled`, `otelServiceName` (`<user>@<host>:<script>` outside Kubernetes, the namespace and pod inside),
  `tz_name`, `tz_utc_offset_seconds` and an ISO 8601 local `asctime`; `created` is the UTC timestamp "for computers to
  read and compare", `asctime` the local one "for humans".
